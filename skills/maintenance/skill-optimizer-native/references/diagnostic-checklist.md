# Skill 诊断清单

仅在需要逐维审计或比较修复方案时加载。先读目标、调用方、消费者和现行契约，再使用
[撰写规范](authoring-conventions.md) 判断执行形态。此清单帮助定位问题，不是所有 Skill
必须拥有的章节、示例或 Gate 清单；宪法与登记的真相源优先于
[通用实战手册](skill-writing-handbook.md)。

## A. 任务与边界

- 用户要完成什么？Skill 的起点、终点与可观察结果是否清楚？
- description 是否准确覆盖该任务，并避开容易混淆的相邻 Skill？仅对自动触发 Skill 评估触发边界。
- 现有 mode、脚本或 reference 能否处理该任务？新能力是否通过宪法 §5 准入？
- 用户已授权的动作和需要另行授权的外部写入是否分清？

## B. 输入、路由与失败

- 主管和员工是否只消费当前任务的版本、输入引用、读写范围和验收契约？宿主是否真实执行委派？
- 函数型桥接是否有可执行参数/返回契约、资源探活、路径约束和明确错误状态？
- 必需输入缺失、版本未知、Schema 不匹配时是否显式失败？可选输入降级是否有原因？
- 退休资料是否仅作为历史数据保留，未登记为生产方法或宿主可执行入口？

## C. 输出与消费者

- 下游真实读取哪些字段或文件？是否有只为填满 Schema 而生成的 artifact？
- 输出示例若存在，是否符合当前 Schema？SKILL.md 是否又复制了一份可演化的契约？
- 判断型输出能否定位理由、证据和修复目标？是否使用伪精确分数门控？
- 修改输出后，消费者、校验器和相关评估用例是否同步？

## D. 上下文与成本

- 每次调用都读到的内容是否每次都需要？原始材料与大成果 能否只传引用？
- 岗位、方法与 reference 的分工是否清楚？是否重复加载同一语义？
- 当前流程强度是否与任务风险和价值相称？新增步骤是否带来可验证的边际收益？
- 行数与常驻 Prompt 预算查询 `config/system/complexity-budget.yaml`，不要套用通用手册的数字。

## E. 机制与安全

- 状态、计数、路由、格式和机械验证是否交给确定性执行器（C1/C2）？
- 新 Gate 是否对应真实失败类、最早稳定拦截点和退路（C6）？
- 脚本是否验证外部输入、路径、权限和必需依赖？诊断输出是否避免泄露密钥？
- 删除、覆盖、发布或外部写入是否遵守授权与现有安全边界？

## F. 评估与腐烂检测

- 有什么已发生或明确举证的失败？评估能否观察到修复后的行为，而非只匹配措辞？
- 自动触发 Skill 检查命中与误触发；员工检查输出或决策；桥接检查契约与失败状态。
- `PYTHONPATH=src python -m textpicos.maintenance.eval_skill <目标> --validate-only` 只证明用例结构合法；行为结果需另有记录。
- 结构变更后运行相关测试、文档漂移检查与 `bash scripts/audit.sh --scope system`，并区分既有 FAIL 与新回归。

## 输出方式

按影响排序列出「症状 → 根因 → 证据 → 最小修复 → 验证」。没有证据的问题写成待核实项。
定性判断用可定位 finding、理由和硬 KO；量化只采用确定性测量，不给 Skill 打加权总分。
