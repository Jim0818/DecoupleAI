# Natural Prose — 朴素自然正文

这不是“去 AI 检测器”，也不是作者人格包。它只解决一件事：**手里已有可靠材料时，怎样用普通、自然、连续的中文把事情讲下去。**

核心判断：

> 上一句刚交出了什么，下一句就处理什么。重要处多讲，普通处普通讲；判断靠近证据，事情讲完就停。

## 1. 适用边界

本 Skill 只处理表达与局部结构，不负责补事实、补证据或选角度。Revision 2 可依真实事实补少量非关键情境细节，边界见 §5。

| mode | 使用者 | 任务 |
|---|---|---|
| `compose` | Writer | 从已有材料直接生成自然正文 |
| `review` | Body Reviewer | 判断表达问题是否真的损害理解、可信度或阅读任务 |
| `refine` | Refiner | 只修命名 finding，优先删除和局部重排 |

调用者已有 Writing Contract、Claim Ledger、review schema 或 change manifest 时，**外层契约始终优先**。本 Skill 不另造一套输出 envelope。

## 2. 五条总原则

### 2.1 先处理事情，允许人正常说话

正文像懂行的同事讲清一件事：先交代具体对象或问题，用直接动词说明动作，再顺着事实、机制、步骤、例子、结果和有边界的判断推进。可以自然使用“但、所以、比如”等承接，它们要承担真实关系，不按段落撒口头禅。允许有用的叙事停顿和取舍，不为了“更像人”强造金句、反转或作者姿态。

### 2.2 新句新段要推进当前内容债务

先确定一条读者任务或核心问题线。每个新单元至少完成一个真实动作：补事实、补原因、给例子、解释术语、比较、说明限制、回答问题、推进状态或做必要判断。内部覆盖清单只确保内容齐全，不决定正文的顺序和标题。

同一结论换一套说法，不算推进。

### 2.3 结构优先藏在局部语义关系里

正常正文不需要不断告诉读者“下面讲什么”。优先让相邻句段形成接力：对象续接、结果补因、机制落地、问题直答、限制回压。

只有认知任务真正换层时，才考虑显式结构。

### 2.4 有取舍，也有证据附近的判断

核心机制充分展开，共同背景简短处理，无关材料删去或移出本篇。评论只有在帮助读者理解后果、比较路径、做选择、识别证据缺口或明确未知项时才出现。

评论完成后回到材料，不单独搭建“作者观点层”。

### 2.5 完成即停止

读者任务已完成、必要边界已交代，就结束。Revision 2 的硬技术稿若用了 H2，最后一节按结构政策用 `## 写在最后` 收束已有问题、选择或边界；不重复全文，也不补“时代意义”。无 H2 的稿件自然停下。

## 3. 自然推进的十个动作

详细说明和 before/after 见 `references/progression.md`。写作时优先从这十个动作里选择下一步，而不是选择一种“高级转场句式”。

1. **对象续接**：继续处理上一句已经出现的人、产品、数字、问题或结果。
2. **结果补因**：先交结果，再解释为什么会这样。
3. **抽象落地**：判断后给任务、数字、操作、命令、案例或后果。
4. **定义随用随补**：术语真正阻碍理解时再解释。
5. **例子承担证明**：例子必须改变读者理解，不做装饰；若承诺以一个案例贯穿，后文每次回到它都推进动作、状态或边界，做不到就收窄承诺。
6. **具体问答**：只问文章马上会回答的真实问题。
7. **评论贴证据**：事实足够后给有限判断。
8. **限制回压**：优点之后补真正影响结论的失败、缺口或范围。
9. **允许密度不均**：普通处一句带过，核心机制可以连续多段。
10. **停止**：当前问题已经处理完，不再制造新部分。

## 4. 结构路由

### 4.1 `continuous_editorial`

Revision 2 的普通文章、情报、产品更新、工具介绍、行业观察、普通分析、复盘和一般教程均采用这一类。历史 revision 1 仍按已锁定契约读取。

默认要求：

- narrative H2 = 0；
- 不用 H3/H4、`01 PART`、单行粗体总结、`写在最后` 等伪标题代偿；
- 不用“背景 / 核心变化 / 真正影响 / 最后怎么看”式目录推进；
- 背景随当前理解缺口补入；
- 段落之间靠内容关系衔接。

情报类具体写法见 `references/intelligence-writing.md`。

### 4.2 `sectioned_editorial`（仅 revision 1 回放）

普通文章、叙事、复盘、分析、教程或工具稿确有导航价值时允许 H2，也可以不用。分节依据是读者需要定位不同任务、阶段或问题，不是题材、字数和固定数量。小标题优先说明对象、动作、变化或本节职责，不强制写成金句或态度。

### 4.3 `hard_technical`

硬核技术文 **H2 allowed, not required**。出现代码或安装命令本身不构成硬技术分节理由；用了 H2 时服从正文结构政策的末节规则。

只有下列认知换层确实需要导航时才开 H2：

- 是什么 → 怎么实现；
- 机制 → 实验/验证；
- 原理 → 安装/操作；
- 一个技术层级 → 另一个技术层级。

H2 优先用对象名、组件名、任务名或实验名，不用“真正的突破”“最值得关注”这类评论标题。

技术保护规则见 `references/hard-tech-writing.md`。

## 5. 信息权限、知识来路与作者存在感

第一人称可以承担信息权限与明确的当前选择：

- 我怎么知道；
- 我实际做了什么；
- 我为什么这样选；
- 我哪里失败；
- 哪一点只是我的判断或仍拿不准。

没有亲历材料，可以完全不写“我”，也可以在证据支持时写条件推演，例如“如果我来配置，会先把重试限制在幂等请求上”。这种表述不能变成过去时部署、踩坑、收益或用户反馈。缺第一人称、缺故事、缺鲜明观点本身都不是缺陷。

source-led 正文在**知识来路会改变可信度或解释**时，可以保留一次来源核对、材料取舍、真实判断变化或未知项；也可以完全用中性归属表达。是否能写“我查了 / 我试了 / 我改了判断”，必须服从 Author Input 与 first-person permission，不能把公开材料升级成亲历。

Revision 2 可依已有真实事实补少量非关键时间、动作或环境细节，让事情更容易讲明白；公开正文无须逐处标注。它们不得改变事实骨架、技术操作、结果、因果或来源身份，不得写成未经确认的亲测、部署、报错、收益或用户反馈，也不得进入 Evidence Kernel 或真实 Author Context。若一处细节会让读者误认作者亲历了来源案例，应改写或删去。

知识来路不是新配额。不要每隔两段重复“公开资料显示 / 目前无法确认 / 可以确认的是”，让后台核验笔记接管正文。具体写法见 `references/epistemic-texture.md`。

## 6. 开头

开头尽快碰到本文对象，并让后文承接它。Revision 2 优先考虑与主线相关的近期事件、真实经历、具体结果或问题；没有合适材料时直接进入对象。事件应交代它为什么影响本文对象，经历应带出后续问题或选择。入口可以是：

- 事件；
- 真实任务；
- 具体问题；
- 已发生的结果；
- 确认过的真实场景；
- 必要定义。

版本、口径和限制贴近它们约束的事实，必要边界仍在首次影响可信度的位置交代。不要先预告文章结构，也不要在首段堆满后台核验说明。

## 7. `compose` 模式

1. 先读取调用者给出的 reader task、required coverage、材料与边界。
2. 服从调用者给出的结构类与 `prose_policy_revision`；缺少 revision 按历史 revision 1 解释。
3. 在能引出主线的具体材料中选开场入口，尽早碰到正文对象。
4. 写每个句段时，只问一个内部问题：**前面刚留下什么需要处理？**
5. 优先用 §3 的推进动作继续，不为了节奏制造短句、转折、排比或总结。
6. 需要评论时，把判断放在相关事实附近，并写清边界。
7. 来源核对、真实判断变化或未知项会改变读者判断时，按 §5 保留最短必要知识来路；无此必要就不显式展示。
8. 事实细节要改变证据、机制、成本、选择、边界、失败原因或下一步行动之一；少量非关键情境细节按 §5 处理。
9. 技术任务保护代码、参数、命令、条件链、实验口径和必要长段。
10. reader task 完成后停止。

输出只交调用者要求的正文或结构化产物，不报告“用了哪些人味技巧”。

## 8. `review` 模式

Review 不检查“像不像人”，只判断表达是否伤害：正确性、理解、证据边界、导航、可操作性或任务完成。

优先识别这些问题动作：

- 新段没有新增内容，只是复述；
- 相邻句段对象突然断开，读者不知道为什么跳到下一件事；
- 背景提前成块，当前还用不上；
- 抽象判断迟迟没有事实、数字、例子或机制落地；
- 开场堆放版本、免责声明与覆盖目录，具体对象和问题迟迟不出现；
- 事件或经历与后文没有因果或问题上的接续；
- 评论说得比证据大，或离证据太远；
- 连续制造“真正 / 本质 / 更深一层”式假升级；
- `continuous_editorial` 用 H2 或伪标题代替语义接力；
- revision 1 的 `sectioned_editorial` 把每个 coverage item 机械变成一节；revision 2 普通稿出现任何可见分节；
- 技术正文为了“自然”丢掉参数、条件、代码或机制；
- 非关键情境细节越界成亲历或证据，或连续装饰而拖慢理解；
- 来源归属和核验说明反复出现，把后台查证笔记写成机构腔；
- 动作长期被“进行了 / 实现了 / 完成了对……”一类名词化结构藏起来，主干因此难读；
- 正文已经完成，却继续总结、升维或写 CTA。

以下情况**不能单独构成 finding**：

- 出现冒号、破折号、问句或“不是 A 而是 B”一次；
- 出现“其实、不过、所以、比如”；
- 没有第一人称；
- 段落长短不均；
- 技术段很长；
- 硬核技术文存在直接的导航 H2。
- revision 1 的普通文章存在有用、顺口的导航 H2；revision 2 的硬技术稿按需使用导航 H2。

确定性 prose signal 只能作为候选位置，不能代替判断。

## 9. `refine` 模式

只修调用者允许的 finding。先做一件事：**识别并保护已经成立的自然部分**，包括有证据的知识来路、真实的不确定性、确实发生的判断变化、有工作的细节，以及材料自然形成的长短不均。不要为了“精修”把它们磨平。

随后按优先级修：

1. 删除重复解释、空评论、自动升维和完成后的尾巴；
2. 合并只换说法的段落；
3. 调整局部顺序，让对象、结果、原因和例子重新接上；
4. 把抽象判断还原到已有事实、动作或边界；
5. 动作被名词化、主干明显来得太晚时，优先恢复直接动词；
6. 必要时修一句转场；保留有用且未越界的少量情境细节，不增加新观点、新证据或无关故事。

具体修复动作见 `references/revision-actions.md`。

Refiner 不做全篇“人味美容”，也不把技术内容缩短成移动端短句。

## 10. 不采用的伪规则

本 Skill 明确不使用以下方法：

- 固定短句率、段落长度或句长方差；
- 第一人称、观点、设问、金句数量配额；
- 禁冒号、禁破折号、禁某一种正常中文句式；
- 为“活人感”主动添加粗口、错字、括号吐槽、假场景；
- 强制每篇有故事、冲突、反转或升华；
- 把任何单一博主的口头禅当默认风格；
- 用加权分数评价“人味”。

字面形式只有在**重复执行坏动作**时才值得修，例如连续用同一种翻案句制造假洞察。

## 11. Before / After

**Before**

```text
真正值得关注的，不是这次模型参数又多了多少，而是整个行业正在发生一次深层重构。
更重要的是，这背后意味着开发者的工作方式会被彻底改变。
下面我们从三个方面来看。
```

**After**

```text
这次更新先改了两件和开发者直接相关的事：上下文窗口扩大，批量调用价格也降了。
如果你的任务本来就要一次塞进长文档，前一个变化马上能用上；高频 API 任务则更受价格影响。
再往下看，真正需要确认的是限流和稳定性有没有一起变化。
```

改动目标不是“更口语”，而是让对象、变化和下一步问题直接出现。

## 13. Constraints

- 不创造用户未提供或证据未支持的经历、事实、引语、结果、来源核对过程和作者判断。
- 不用“作者存在感不足”作为返工理由。
- `continuous_editorial` 不以 H2/H3/H4 或伪标题代偿结构。
- `sectioned_editorial` 与 `hard_technical` 的 H2 允许但不强制，不按数量验收。
- `hard_technical` 不因自然写作压缩必要技术细节。
- 不把字面词句当独立质量门；判断坏的是动作与上下文。
- 不把局部修复扩展成全篇重写。
- 不输出加权“人味分”。
- 调用者契约、证据边界与发布安全始终高于本 Skill。
