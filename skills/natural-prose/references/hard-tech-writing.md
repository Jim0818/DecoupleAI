# Natural Prose · 硬核技术正文

> 用于源码、架构、论文、算法、教程、benchmark、工程实现和排障。

## 1. H2 是导航工具，不是篇幅配额

`hard_technical` 允许 H2，但不要求。

优先在认知任务真正换层时使用：

- 定义 → 实现；
- 实现 → 数据流 / 控制流；
- 机制 → 实验；
- 原理 → 安装 / 配置；
- 结果 → 限制 / 排障；
- 一个组件 → 另一个独立组件。

单对象线性依赖链可以从头连续写到底。

### 好的 H2

```text
请求如何进入 Runner
工具调用的数据流
安装与环境变量
消融实验
失败模式
```

### 不推荐的 H2

```text
真正的突破
最值得关注的是
更深一层的问题
为什么它会改变一切
```

前者帮助定位技术对象，后者主要在表演评论。

## 2. 技术细节保护区

以下内容不能为了“更自然”被压缩或散文化：

- 代码块；
- 命令、路径、参数、版本；
- 输入输出 schema；
- 关键配置；
- 实验条件与测量口径；
- 性能数字；
- 失败模式；
- 前置依赖；
- 必要的长条件链。

完整技术关系允许长句、长段和列表。

## 3. 技术推进链

常见自然关系：

```text
对象 → 定义 → 输入/处理/输出 → 关键条件 → 示例/代码 → 结果 → 比较 → 限制
```

不是每篇都要完整走一遍。读者已经知道的层级直接略过。

## 4. 第一人称区分亲历与条件选择

技术稿不需要为了“作者性”加入第一人称。只有第一人称能准确标明证据来源时再用，例如：

- 实际运行环境；
- 输入材料；
- 报错；
- 改动；
- 结果；
- 最后采用的方案。

```text
我先按默认配置跑了一次，29B 模型在 24GB 内存下直接 OOM。把 batch size 从 8 降到 2 后能跑，但吞吐下降明显。
```

这类第一人称的价值是标明证据来源，不是增加人格感。没有真实过程证据时，直接写技术事实和边界即可。

没有亲历材料时，仍可在证据支持下表达当前选择：

```text
如果我来配置，会先把重试限制在幂等请求上；写操作要等幂等键和去重逻辑就绪后再开。
```

这是条件推演，不表示已经上线验证。不得改写成“我在线上踩过这个坑”或补出未发生的收益。

不要在每个技术块前补“我觉得很震撼”。

## 5. 代码前后只补理解增量

代码前说明它要完成什么、读者该看哪个参数、相对上一步变了什么。代码后只补关键行为、可观察结果、容易误解之处或下一步边界。不要逐行翻译代码；也不要为了轻松感删掉参数、命令和失败条件。

正文若说示例实现了反馈、重试或停止条件，代码或伪代码也要展示相应的数据回流与判断；尚未实现的能力就地说明，不靠结尾的笼统免责声明补救。

## 6. 五个高发伪自然问题

1. 每个结果后自动写“这意味着”；
2. 为了故事性把正常安装过程包装成踩坑戏剧；
3. 把标准技术术语换成自造概念；
4. 为了移动端连续拆成单句；
5. 技术结论结束后突然升到行业革命。

修复时优先恢复事实和工程关系，而不是寻找另一种更漂亮的表达。
