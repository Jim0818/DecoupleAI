# 内容写作与修订

围绕读者要理解或完成的事情组织可靠材料。技术解释可以构成全文；有据的取舍、反应和判断按作用保留，不要求每篇提供个人经历或独特观点。

## 选择模式

- `compose`：检查材料能否回答当前问题，选择需要展开的机制、过程或案例。复杂技术稿按需使用 [技术结构](references/technical-structure.md)。开头属于正式正文；需要定位和修复开头问题时按需读 [开头与承诺](references/opening.md)。
- `edit`：已有完整原稿时使用 [原稿与改动保护](references/editing.md)。保留正确事实、有效细节和已经自然的段落，只修本次确有必要的地方。
- `repair`：处理定位明确的问题；局部范围无法安全修好时报告阻塞，不能把局部任务扩大为全文重写。
- `title` / `summary`：使用 [标题与摘要](references/titles.md)，围绕指定版本产出或修改公开文案。标题任务不修改无关正文。

自然表达使用共享 `natural-prose` 的相应模式与任务给出的有效结构政策。账号配置决定受众、深度和声音范围，不改变证据身份。遇到开头绕远、解释跳步、重复收束或过度改稿时，按需读取 [编辑决策示例](references/editorial-examples.md) 的相关部分；无需每稿通读参考。

## 写作

先区分原稿、事实来源、真实作者材料和表达参考。摘要不能支撑关键机制、操作过程或结果时，按需读取相应原文片段、代码和记录，不从概括中猜细节；也不默认打开全部来源。资料不足就缩小问题或向主管说明会影响结论的缺口。

给核心机制和有用案例足够篇幅，背景随理解需要补入。覆盖清单用于检查遗漏，正文顺序由问题、证据和操作依赖决定。普通情报连续展开；硬技术按有效结构政策分节。

用当前材料进入主线，必要版本与范围靠近相应事实。判断写清依据与条件，真实反应保留其来由；没有真实运行、踩坑或反馈就不能写成亲历。任务完成后检查是否仍在重复收束，保留真正增加解释、条件或下一步动作的部分。

按任务 `input_refs` 的用途与选择理由读取相关片段。`style_reference` 只迁移编辑方法，不借用人物、经历或结论；`approved_edit` 仍须核对前后对照及明确认可来源，标签本身不证明认可。教学示例、现稿、发布或审阅通过不自动成为偏好样本；缺少认可材料时正常写作，无须补一套文件。

## 交付

直接交付任务允许的正式稿件或补丁，标题与摘要随同一成果处理。执行同次必需 visual 方法的 integrate（标题/摘要用 preserve）模式：保留代码、图片、链接及来源关系，将实际配图放在对应论证段落；取图失败时原位保留可见待补图块，不只交一份文外配图清单。缺图块是用户要求的草稿信息，不按内部标记自动删除。不要另写结构蓝图、精修说明或重复整篇正文；主管只需要成果引用、必要变更和未解决项。

用户提供的原稿是本次正式编辑输入，不降格为仅供研究的参考。完整文章交付或接入发布功能时按需读取 [文章交付](references/delivery.md)；纯措辞、标题或局部修订保留已有 frontmatter、文件身份与未涉及的资源。
