# 编辑决策示例

在 compose / edit 遇到相应问题时读取相关部分；repair 仅用于当前允许修复的问题。title / summary 无需默认加载。本文件是教学材料，不是用户认可的范文，不提供新稿事实，也不是统一句式模板。迁移的是编辑决定，人物经历、产品结论和例子内容须由当前材料另行支持。

## 开头有亲历包装，材料只有机制说明

已有材料：程序逐行读取记录，随后把全部记录保存在同一个列表；没有作者操作记录。

原表达：前几天我处理数据时遇到一个问题，文件一大，内存就不够了。

可改：逐行读取之后，记录去了哪里？如果又把每条记录加入同一个列表，列表仍会不断增长。需要一起检查读取方式和后续存储。

编辑决定：从材料中真正需要解释的机制进入。问句可换成直接陈述；不能把“前几天我”换成另一个未经支持的故事。

## 例子很多，读者仍不知道下一步怎么做

已有材料：工具安装完成后需新开终端，再执行版本命令确认 PATH 生效；没有用户反馈。

原表达：安装是第一步，配置也很重要。比如，团队使用时需要注意环境一致性。

可改：安装完成后，新开一个终端，再运行版本命令。若仍提示找不到命令，先确认安装目录已经加入 PATH，再继续后面的配置。

编辑决定：用当前操作的预期状态和失败分支补足解释。例子不能只增加熟悉的团队场景；这里只能据已提供的安装要求写，不能声称实际测试成功。

## 结尾多次给出同一建议

已有材料：某个工程层只在特定故障出现后才值得添加，正文已经讲清代价与条件。

原表达：不必一开始把所有层都补齐。更重要的是按实际问题选择。最后，适合自己的方案才是好方案。

可改：先定位当前故障，再补对应的一层；增加后检查它是否解决了原来的问题。

编辑决定：保留已有条件和可执行动作，合并重复劝告。如果后文还补充了新的边界、真实反应或必要回扣，就不因它位于结尾而删除。

## 轻编辑把原本清楚的话磨成通用说明

已有原稿：命令能跑了，结果却还是空的。先别换模型，看看输入文件有没有真正传进去。

过度改写：需要关注执行链路各环节的协同情况，确保输入与输出之间形成有效闭环。

编辑决定：原稿的观察、停顿和排查动作已经有效，可以原样保留。若实际问题是后面缺少检查路径，只补材料支持的路径或命令；不用“我觉得”、热络称呼或抽象概括替换它。

## 使用认可改稿

从任务的 `input_refs` 按当前编辑问题选用相关示例。提供了用户明确认可的前后对照时，核对其认可来源、解决的问题、适用情境和保护内容；`purpose=approved_edit` 只是用途声明。没有认可材料就按当前任务完成写作，不扫描整库或要求先补样本。认可文风不代表事实已核验，也不能把其中的经历、数字或结论带入新稿。
